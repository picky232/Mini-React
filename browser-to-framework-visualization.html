클릭에서 화면까지: 브라우저와 미니 리액트가 함께 일하는 순서

버튼 한 번을 누르면 이벤트 루프, setState, hooks 배열, Virtual DOM, diff, patch, Layout·Paint가 차례로 움직인다. 이 페이지는 할 일 앱의 [추가] 클릭 하나를 처음부터 끝까지 따라가며, 각 단계에서 무엇이 왜 바뀌는지 보여준다.

왜 필요할까

바닐라 JS로 화면을 만들면 상태가 바뀔 때마다 관련된 DOM을 사람이 직접 찾아 고쳐야 한다. 고칠 곳을 하나만 빠뜨려도 상태와 화면이 어긋난다. 프레임워크는 "상태만 바꾸면 화면은 알아서 맞춘다"는 약속(선언형, UI = f(state))으로 이 문제를 없앤다.

명령형 (바닐라): 어떻게 고칠지 내가 쓴다
todos.push(text);ul.appendChild(makeLi(text));   // 1. 목록에 추가countEl.textContent = todos.length + '개'; // 2. 개수 갱신input.value = '';               // 3. 입력창 비우기// 하나라도 빠뜨리면 화면과 상태가 어긋난다
선언형 (프레임워크): 결과만 쓴다
setTodos([...todos, text]);setText('');// 화면 모양은 App()의 return이 정한다// 무엇을 고칠지는 diff가 찾는다

DOM 조작이 느린 진짜 이유

DOM API를 부르는 것보다, 그 뒤에 브라우저가 다시 해야 하는 계산이 비싸다.

무엇을 바꾸면브라우저가 다시 하는 일예시
크기·위치·구조Reflow(Layout): 위치·크기를 다시 계산하고, 그 뒤 Paint까지 한다. 부모·형제에게도 번질 수 있다.width, margin, 노드 추가·삭제, 글자 내용
겉모습만Repaint(Paint): 위치는 그대로 두고 픽셀만 다시 칠한다.color, background
합성 속성Composite만: 이미 칠한 레이어를 GPU가 옮기거나 투명도만 바꾼다.transform, opacity

비유: 집 리모델링

집주인(사용자)의 요청을 받아 설계도를 고치고, 바뀐 곳만 공사하는 리모델링 회사로 생각하면 흐름이 한 줄로 이어진다.

구성 요소

아래 시뮬레이터에 나오는 칸들이다. 파란색은 브라우저, 초록색은 미니 리액트의 것이다.

브라우저 이벤트 루프

메인 스레드는 한 번에 하나만 실행한다. 콜 스택(지금 실행 중인 함수들)이 비면 마이크로태스크 큐(Promise, queueMicrotask, MutationObserver)를 전부 비우고, 그다음 화면을 그릴 기회를 갖고, 그다음 태스크 큐(클릭, setTimeout)에서 하나를 꺼낸다.

미니 리액트 hooks 배열

컴포넌트 인스턴스에 붙은 배열이다. App 함수는 매번 새로 실행되지만 이 배열은 남아 있다. hookIndex가 0부터 하나씩 올라가며 "몇 번째 hook인가"로 칸을 찾는다.

미니 리액트 VDOM과 diff

{ type, props, children } 모양의 JS 객체 트리다. diff는 두 트리를 같은 위치끼리 비교해 추가 / 삭제 / 타입 교체 / 텍스트 변경 / 속성 변경 중 하나로 기록한다.

브라우저 실제 DOM과 렌더링 파이프라인

DOM이 바뀌어도 바로 픽셀이 되지 않는다. Render Tree → Layout → Paint → Composite를 거쳐야 화면에 보인다. 이 계산은 JS가 끝난 뒤 한 번에 한다.

헷갈리는 점

    

      
setTodos 바로 다음 줄에서 todos를 찍으면 왜 옛 값일까?
setState는 hooks 배열의 값을 바꿀 뿐이다. 지금 실행 중인 App()의 지역 변수 todos는 이번 렌더가 시작될 때 꺼내 온 값이라 그대로다. 새 값은 다음 렌더에서 useState가 hooks 배열을 다시 읽을 때 보인다.

      
patch가 끝났는데 왜 화면이 아직 그대로일까?
DOM이 바뀐 것과 픽셀이 바뀐 것은 다르다. 브라우저는 JS가 실행되는 동안 그리지 않는다. 콜 스택과 마이크로태스크 큐가 모두 빈 뒤 다음 프레임에서 Layout·Paint를 한 번에 한다.

      
input의 value 변경은 왜 MutationObserver에 안 잡힐까?
input.value는 JS 속성(property)이다. DOM 트리의 속성(attribute)이 바뀌지 않으므로 기록이 생기지 않는다. setAttribute('value', …)로 바꾸면 기록은 생기지만, 사용자가 이미 타이핑한 입력창의 글자는 바뀌지 않는다.

      
VDOM이면 항상 직접 DOM을 고치는 것보다 빠를까?
아니다. 바뀔 곳을 정확히 아는 명령형 코드가 가장 빠르다. VDOM은 VDOM 생성과 diff 비용을 더 낸다. 대신 "어디를 고칠지"를 사람이 신경 쓰지 않아도 되면서 충분히 빠르게 해 준다.

    

  


  

    
핵심 정리

    
    
      
  • setState는 값을 hooks 배열에 저장하고 리렌더를 예약한다. 바로 그리지 않아서 여러 setState가 한 번의 렌더로 묶인다.
    • 
      
  • 함수는 매번 새로 실행되지만 상태는 함수 밖 hooks 배열에 있고, 호출 순서로 찾는다. 그래서 hook은 조건문 안에 두면 안 된다.
    • 
      
  • diff로 고른 곳만 patch하면 브라우저가 다시 계산할 범위가 줄어든다. 픽셀은 JS가 끝난 뒤 Layout·Paint를 거쳐 한 번에 바뀐다.
    • 
    

    
확인 질문

    
같은 핸들러에서 setState를 3번 부르면 App()은 몇 번 실행될까?
한 번이다. 첫 setState가 update()를 마이크로태스크로 예약하고, 나머지는 scheduled 플래그를 보고 예약을 건너뛴다. 핸들러가 끝난 뒤 update()가 한 번 실행된다.

    
목록 맨 앞에 '빨래'를 넣으면 인덱스 기반 diff는 무엇을 기록할까?
li 세 개가 모두 한 칸씩 밀려 비교된다. 앞의 두 li는 '텍스트 변경', 마지막 자리는 '추가'로 기록된다. 실제로는 노드 하나만 끼워 넣으면 되는 일이다. 실제 React는 key로 같은 항목을 찾아 이동만 한다.

    
patch 도중에 ul.offsetHeight를 읽으면 무슨 일이 생길까?
브라우저는 정확한 높이를 돌려줘야 하므로, 모아 두었던 변경을 그 자리에서 반영해 Layout을 강제로 실행한다(강제 동기 레이아웃). 읽기와 쓰기를 번갈아 반복하면 Layout이 여러 번 일어난다(Layout Thrashing).

    
useState의 초기값 '빨래'는 두 번째 렌더에서 왜 무시될까?
useState는 hooks[i]가 비어 있을 때만 초기값을 쓴다. 두 번째 렌더에서는 hooks[0]에 이미 값('')이 있어서 그 값을 돌려준다.
