# 미니 리액트 개념 정리: 한 층 위에서 보기

코드는 AI가 쓸 수 있다. 사람에게 남는 일은 **왜 이런 구조인지, 무엇을 얻고 무엇을 포기했는지**를 설명하는 것이다.
이 문서는 각 개념을 **문제 → 아이디어 → 대가(트레이드오프)** 순서로 정리한다.

---

## 0. 전체 그림

React가 푸는 문제는 하나다.

> **"데이터가 바뀔 때마다 화면을 어떻게 맞춰 줄 것인가?"**

이 문제를 세 층으로 나눠 푼다.

```
[무엇을 보여줄까]   컴포넌트 + state     ← 개발자가 "설계도"를 쓴다
        ↓
[무엇이 달라졌나]   가상 DOM + diff      ← 라이브러리가 이전·새 설계도를 비교한다
        ↓
[어떻게 반영할까]   patch → 실제 DOM     ← 라이브러리가 바뀐 곳만 시공한다
```

각 층은 바로 아래 층의 세부를 모른다. 개발자는 DOM API를 모르고, diff는 state를 모르고, patch는 컴포넌트를 모른다. **이렇게 관심사를 나눈 것이 React 설계의 핵심이다.**

---

## 1. 명령형 vs 선언형

| | 명령형 (바닐라 JS) | 선언형 (React) |
|---|---|---|
| 개발자가 쓰는 것 | "이 노드를 찾아서 글자를 이걸로 바꿔라" | "state가 이럴 때 화면은 이렇게 생겼다" |
| 개발자가 추적해야 하는 것 | 무엇이 바뀌었고, 어느 DOM을 고쳐야 하는지 | 없음. 지금 상태의 화면만 설명 |
| 비유 | 시공 지시서 | 설계도 |

**핵심:** 선언형은 "변화"를 다루던 일을 "상태"를 설명하는 일로 바꾼다. 변화를 계산하는 어려운 일은 라이브러리가 맡는다.

**대가:** 라이브러리가 변화를 대신 계산하는 비용(가상 DOM 생성, diff)이 생긴다.

## 2. DOM: 화면의 실체

**정의:** 브라우저가 HTML을 읽어서 메모리에 만든 **객체 트리**. JS가 화면을 읽고 바꾸는 유일한 창구다.

### 꼭 구분할 것

| | HTML | DOM |
|---|---|---|
| 정체 | 텍스트 파일 | 메모리 안의 살아 있는 객체 트리 |
| 바뀌는가 | 처음 읽힌 뒤 절대 안 바뀜 | JS가 계속 바꿈 |
| 역할 | 처음 화면의 **주문서** | 지금 화면의 **실체** |

- "DOM 수정"은 HTML 파일 수정이 아니다. 메모리의 객체를 바꾸는 것이다.
- `innerHTML`도 HTML 파일을 고치는 게 아니다. 문자열을 주문서로 삼아 **노드 객체를 새로 만드는** 것이다.

### 노드는 "객체"다: 정체성(identity)이 있다

- 노드 하나하나가 고유한 객체다. 글자가 똑같이 "사과"여도 **새로 만든 노드는 다른 노드**다.
- 노드에는 보이지 않는 상태가 붙어 있다. 이벤트 리스너, 입력 중인 값, 포커스, 애니메이션 진행 상태 등이다.
- 그래서 노드를 **버리고 새로 만들면** 이 상태가 전부 사라진다. **그 자리에서 고치면** 유지된다.
- 이 차이가 가상 DOM이 노드를 최대한 재사용하려는 이유다.

### `window`와 `document`

- `window`: 브라우저 창 전체. 전역 공간, 타이머, 주소, 창 이벤트를 가진다.
- `document`: 그 창에 로드된 DOM 트리의 시작점.

## 3. 왜 DOM 조작은 비싼가: 렌더링 파이프라인

DOM을 바꾸면 브라우저는 화면을 맞추기 위해 다음 단계를 다시 할 수 있다.

```
Style → Layout(Reflow) → Paint(Repaint) → Composite
```

| 단계 | 하는 일 | 비용 |
|---|---|---|
| Style | 어떤 CSS가 적용되는지 계산 | 중간 |
| **Layout (Reflow)** | 모든 요소의 크기·위치 계산 | **가장 큼.** 하나가 바뀌면 주변까지 연쇄 계산. DOM이 클수록 비쌈 |
| **Paint (Repaint)** | 픽셀 색 칠하기 | 중간. 색만 바뀌면 Layout을 건너뛰고 여기부터 함 |
| Composite | 레이어 합쳐서 표시 | 작음 |

### "DOM이 느리다"의 정확한 의미

- ❌ DOM 객체 하나를 바꾸는 행위 자체가 느리다
- ✅ **DOM 조작은 일반 JS 객체 조작보다 비싸다.** 무거운 객체이고, 화면 재계산이 따라오고, 브라우저 엔진과 JS 사이의 경계를 넘어야 하기 때문이다

### Layout Thrashing (강제 동기 레이아웃)

- 브라우저는 원래 변경을 모아서 프레임마다 한 번에 계산한다.
- 그런데 **바꾸고 → 크기를 읽고 → 또 바꾸면**, 정확한 값을 주기 위해 매번 Layout을 강제로 다시 한다.
- 교훈: **읽기는 읽기끼리, 쓰기는 쓰기끼리 모아라.** 이 "모아서 한 번에" 원칙이 뒤에 나오는 patch와 batching에도 그대로 이어진다.

## 4. 가상 DOM: 비교를 위한 값싼 사본

**정의:** 실제 DOM 트리를 같은 모양의 가벼운 JS 객체 트리로 옮겨 놓은 것. 노드 하나를 **VNode**라고 부른다.

**VNode는 세 가지 정보만 가진다:** 태그 종류(`type`), 속성(`props`), 자식(`children`). 화면을 다시 그리는 데 필요한 최소한이다.

### 왜 필요한가

| 문제 | 가상 DOM이 주는 것 |
|---|---|
| 비교하려면 "이전"과 "새" **두 벌**이 필요한데, 실제 DOM은 화면에 보이는 한 벌뿐이다 | JS 객체라서 몇 벌이든 만들어 나란히 놓을 수 있다 |
| 매번 화면 전체를 새로 만들면 비싸다 | 화면과 연결되지 않아서 만들고 버려도 싸다 |
| 노드를 버리면 입력값·이벤트가 사라진다 | 비교 결과로 바뀐 곳만 고쳐서 노드를 재사용한다 |
| 과거 화면으로 돌아가기 어렵다 | 그냥 값이라서 배열에 보관하면 history가 된다 |

### 세 가지 방식 비교

| 방식 | 실제 DOM 변경량 | 개발자 부담 |
|---|---|---|
| ① 손으로 최적 조작 | 최소 | 큼. 무엇이 바뀌었는지 직접 추적 |
| ② `innerHTML`로 통째로 다시 그리기 | 최대. 전부 버리고 새로 만듦 | 작음 |
| ③ 가상 DOM | 최소에 가까움 | 작음. ②처럼 전체를 다시 그리듯 씀 |

- **"전부 다시 그린다"의 대상이 다르다.** ②는 비싼 실제 DOM을, ③은 싼 JS 객체를 전부 다시 만든다.
- 속도는 ① ≥ ③ > ② 순서다. ③은 diff 비용이 더해지니 이론상 ①보다 느리다.

### 흔한 오해

> ❌ "가상 DOM은 실제 DOM보다 빠르다"
> ✅ "가상 DOM은 **②의 편함**과 **①에 가까운 성능**을 함께 얻는 **절충안**이다"

증거: Svelte, SolidJS는 가상 DOM 없이 빌드할 때 ①에 해당하는 코드를 자동으로 만든다. 가상 DOM은 성능의 정답이 아니라 하나의 설계 선택이다.

## 5. 역할 분담과 업데이트 흐름

### 누가 무엇을 하는가

| 주체 | 하는 일 |
|---|---|
| **개발자** | "state가 이럴 때 화면은 이렇다"는 설계도(컴포넌트)를 **한 번** 쓴다 |
| **라이브러리** | state가 바뀔 때마다 설계도를 다시 펼쳐 새 가상 DOM을 만들고, 비교하고, 반영한다 |
| **사용자** | 클릭·입력으로 state를 바꾸는 계기를 준다 |

개발자는 가상 DOM 객체를 직접 만지지 않는다. **값만 바꾸면 나머지는 자동**이다.

### 한 번의 업데이트에서 일어나는 일

| 단계 | 하는 일 | 실제 DOM을 건드리나 |
|---|---|---|
| 1. `setState` | JS 쪽 값을 바꾸고, "다시 그려"를 **예약** | ❌ |
| 2. render | 컴포넌트를 다시 실행해 새 가상 DOM 생성 | ❌ |
| 3. diff | 이전·새 가상 DOM을 비교해 변경 목록 작성 | ❌ |
| 4. patch | 변경 목록대로 실제 DOM 수정 | ✅ **여기서만** |

### `setState`의 진짜 의미

- `setState`는 DOM 수정이 아니다. **"바뀌었을 수 있으니 확인해 줘"라는 요청**이다.
- 결과적으로 DOM이 바뀔 수는 있지만 **간접적**이다. 값이 같거나, 바뀐 값이 화면에 쓰이지 않으면 DOM은 그대로다.
- `setState` 직후에는 **JS 값과 화면이 잠깐 어긋난 순간**이 있다. 이 둘을 다시 맞추는 것이 라이브러리의 존재 이유다.
- 값을 변수에 직접 대입하면 라이브러리가 모른다. 반드시 `setState`라는 **정해진 통로**로 바꿔야 한다.

### Phase 1과 Phase 2의 연결

| | 사람이 하는 일 | 트리거 | 새 가상 DOM의 출처 |
|---|---|---|---|
| Phase 1 | 테스트 영역 HTML 수정 | Patch 버튼 | 실제 DOM을 읽어서 변환 |
| Phase 2 | 클릭·입력 | `setState` | 컴포넌트를 다시 실행 |

**트리거와 출처만 다르고, diff → patch는 같은 엔진을 쓴다.**

## 6. Diff: 무엇이 달라졌는지 찾기

**정의:** 두 가상 DOM 트리를 같은 위치끼리 비교해서 "이전 화면을 새 화면으로 바꾸려면 무엇을 해야 하는지" **변경 목록**을 만드는 과정. DOM은 건드리지 않는다.

### 최소 변경을 위한 5가지 판단

같은 위치의 두 노드를 놓고 순서대로 묻는다.

| # | 질문 | 판단 | 노드 재사용 |
|---|---|---|---|
| 1 | 새 쪽에만 있나? | **추가** | 새로 만듦 |
| 2 | 이전 쪽에만 있나? | **삭제** | — |
| 3 | 종류가 다른가? (`li`→`p`, 글자↔태그) | **교체** (아래 전부 새로) | 새로 만듦 |
| 4 | 둘 다 글자인데 내용이 다른가? | **텍스트 변경** | ✅ 재사용 |
| 5 | 같은 태그인데 속성이 다른가? | **속성 변경** | ✅ 재사용 |

5번까지 통과하면 **자식들끼리 같은 질문을 반복**한다(재귀). 트리 전체를 위에서 아래로 훑는 구조다.

### 설계에 담긴 판단

- **"종류가 다르면 아래는 보지 않는다."** 비교 비용을 크게 줄이는 대신, 아래가 거의 같아도 통째로 새로 만든다.
- **"재사용이 기본, 새로 만들기는 예외."** 3번(교체)을 제외하면 기존 노드를 그대로 두고 값만 고친다.

### 한계: 위치(인덱스)로 짝짓기

- 자식을 순서대로 짝지으면, **맨 앞에 하나만 끼워도** 뒤 항목이 전부 "바뀐 것"으로 보인다.
- 원인: "이 항목이 그 항목이다"라는 **정체성 정보가 없다.**
- 해결: React의 `key`. (8장)

## 7. Patch: 바뀐 곳만 시공하기

**정의:** diff가 만든 변경 목록을 받아, 실제 DOM에서 해당 위치를 찾아가 고치는 과정. **유일하게 실제 DOM을 건드리는 단계**다.

- 변경 목록에는 **주소(path)**가 붙어 있다. "루트에서 몇 번째 자식의 몇 번째 자식"이라는 길 안내다.
- 변경 종류마다 쓰는 DOM 기능이 다르다. 글자는 그 자리에서 바꾸고, 속성은 그 자리에서 고치고, 추가·삭제·교체만 노드를 넣고 뺀다.

### 주의할 점

- **같은 부모에서 여러 개를 지울 때는 뒤에서부터.** 앞에서부터 지우면 뒤 노드의 번호가 당겨져서 엉뚱한 노드가 지워진다.
- **비교(diff)와 반영(patch)을 나눈 이유:** 반영을 한곳에 모아 실제 DOM 접촉을 최소화하고, 비교 로직은 화면 없이도 테스트할 수 있게 하기 위해서다.

## 8. MutationObserver: DOM 변화를 관찰하는 눈

**정의:** 지정한 DOM이 바뀌면 **무엇이, 어디서, 어떻게** 바뀌었는지 기록을 모아서 알려 주는 브라우저 기능.

| 관찰할 수 있는 것 | 뜻 |
|---|---|
| 자식 목록 변화 | 노드 추가·삭제 |
| 속성 변화 | `class`, `id` 등 변경 |
| 텍스트 변화 | 글자 내용 변경 |
| 하위 전체 | 대상의 자손까지 감시 |

- 위 세 가지(자식·속성·텍스트) 중 **최소 하나는 켜야** 하고, 하위 전체 감시는 기본으로 꺼져 있다.
- 변경 즉시가 아니라 **모아서 한 번에** 알려 준다.

**과제에서의 가치:** "가상 DOM이 정말 최소만 바꿨나?"를 **숫자로 증명**하는 도구다. 같은 변경을 `innerHTML`과 patch로 각각 해서 기록 개수를 비교하면 된다.

## 9. React가 중요하게 여기는 것

### Reconciliation (재조정)

- 이전 화면과 새 화면을 맞춰 가는 전체 과정을 React는 **재조정**이라고 부른다.
- 우리 구현의 render → diff → patch가 여기에 해당한다.

### Render와 Commit의 분리 ⚠️ 미검증

- **Render:** 컴포넌트를 실행하고 비교한다. 실제 DOM을 건드리지 않는다.
- **Commit:** 비교 결과를 실제 DOM에 반영한다.
- "계산"과 "반영"을 나누는 이유는 6·7장과 같다. 반영을 한곳에 모으고, 계산은 자유롭게 하기 위해서다.

### 두 가지 가정으로 O(n³)을 O(n)으로

- 트리 두 개를 **완벽하게** 비교하는 알고리즘은 O(n³)이라 실제 화면에 쓸 수 없다.
- React는 두 가지를 가정하고 **완벽함을 포기하는 대신** O(n)으로 비교한다.
  1. **종류가 다르면 다른 트리다.** → 아래를 비교하지 않고 통째로 교체한다.
  2. **`key`가 같으면 같은 항목이다.** → 개발자가 정체성을 알려 주면 순서가 바뀌어도 이동만 한다.
- 공식 문서는 이 가정이 실제 사용 사례 대부분에서 맞는다고 설명한다. **"대부분 맞는 가정으로 큰 비용을 줄인다"**는 것이 React diff의 설계 철학이다.

### `key`: 정체성을 개발자가 알려 주는 장치

- 위치가 아니라 **이름표**로 짝을 짓는다.
- 좋은 `key`는 **안정적이고, 예측 가능하고, 고유**해야 한다.
- 매번 바뀌는 값(무작위 값)을 쓰면 매번 새 노드를 만든다. 배열 인덱스는 순서가 바뀌지 않을 때만 괜찮다.
- 다른 부모로 옮겨 간 노드는 React도 "이동"으로 알아채지 못한다. 삭제 후 새로 만든다.

### 우리 구현과 React의 차이

| | 미니 리액트 | React |
|---|---|---|
| 자식 짝짓기 | 위치(인덱스) | `key` (없으면 위치) |
| 렌더 작업 ⚠️ | 한 번에 끝까지 | 작업을 쪼개 중단·재개 (Fiber) |
| 여러 업데이트 ⚠️ | 매번 또는 간단한 묶음 처리 | 자동 묶음 처리(batching), 우선순위 |
| 이벤트 ⚠️ | 노드마다 직접 등록 | 루트에서 한 번에 받는 합성 이벤트 |
| state 위치 | 루트 컴포넌트만 (과제 제약) | 모든 컴포넌트가 각자 가질 수 있음 |

⚠️ 표시는 이번에 공식 문서를 직접 확인하지 못한 내용이다. 발표 전에 [react.dev](https://react.dev)에서 확인한다.

## 10. 관통하는 설계 원칙

여러 장에 같은 생각이 반복해서 나온다.

| 원칙 | 나타나는 곳 |
|---|---|
| **비싼 것은 아끼고 싼 것으로 대신한다** | 실제 DOM 대신 가상 DOM으로 비교 |
| **계산과 반영을 나눈다** | diff / patch, Render / Commit |
| **모아서 한 번에 한다** | 브라우저의 프레임 단위 계산, MutationObserver, batching |
| **정체성을 지킨다** | 노드 재사용, `key` |
| **완벽함 대신 대부분 맞는 가정** | 종류가 다르면 통째로 교체 |
| **정해진 통로로만 바꾼다** | `setState`를 거쳐야 화면이 따라옴 |

## 11. 용어 사전

| 용어 | 한 줄 정의 |
|---|---|
| DOM | 브라우저가 HTML을 읽어 메모리에 만든 객체 트리. 화면의 실체 |
| 노드 | DOM 트리의 한 칸. 태그(Element), 글자(Text), 주석(Comment) 등 |
| `window` | 브라우저 창 전체이자 전역 공간 |
| `document` | DOM 트리의 시작점 |
| 렌더링 파이프라인 | DOM이 화면이 되기까지의 단계: Style → Layout → Paint → Composite |
| Reflow (Layout) | 요소의 크기·위치를 다시 계산하는 것. 가장 비싼 단계 |
| Repaint (Paint) | 픽셀을 다시 칠하는 것 |
| Layout Thrashing | 쓰기와 읽기를 번갈아 해서 Layout이 반복 강제되는 현상 |
| 가상 DOM | 실제 DOM을 흉내 낸 가벼운 JS 객체 트리 |
| VNode | 가상 DOM의 노드 하나. 종류·속성·자식만 가짐 |
| 선언형 | "어떻게 바꿀지" 대신 "어떤 상태인지"를 기술하는 방식 |
| 컴포넌트 | 화면 일부를 설명하는 설계도. state를 받아 가상 DOM을 내놓음 |
| state | 바뀔 수 있는 데이터. 바뀌면 화면이 따라와야 하는 값 |
| `setState` | state를 바꾸고 다시 그리기를 예약하는 정해진 통로 |
| render | 컴포넌트를 실행해 새 가상 DOM을 만드는 단계 |
| diff | 이전·새 가상 DOM을 비교해 변경 목록을 만드는 단계 |
| patch | 변경 목록을 실제 DOM에 반영하는 단계 |
| path | 변경할 노드의 위치 주소 |
| Reconciliation | 이전 화면을 새 화면으로 맞추는 전체 과정(React 용어) |
| `key` | 리스트 항목의 정체성을 알려 주는 이름표 |
| Batching | 여러 state 변경을 모아 다시 그리기를 한 번만 하는 것 |
| MutationObserver | DOM 변화를 모아서 알려 주는 브라우저 기능 |
| State History | 가상 DOM을 차례로 보관해 뒤로·앞으로 이동하게 하는 기록 |

## 12. 헷갈렸던 질문 Q&A

**Q. DOM을 수정한다는 건 HTML 파일을 고친다는 뜻인가?**
A. 아니다. HTML 파일은 처음에 한 번 읽히고 끝이다. 수정되는 것은 메모리에 있는 객체 트리다. 새로고침하면 JS로 바꾼 내용은 사라진다.

**Q. 가상 DOM도 결국 실제 DOM을 바꾸는데, 그럼 DOM이 느린 게 아니지 않나?**
A. 맞다. DOM 변경 한 번의 비용은 똑같다. 가상 DOM은 직접 조작보다 빠른 게 아니라 **통째로 다시 그리기보다** 빠르다. 실제 DOM을 건드리는 **횟수**를 줄이는 것이다.

**Q. 가상 DOM도 "전부 다시 그린다"면 `innerHTML`이랑 뭐가 다른가?**
A. 전부 다시 만드는 **대상**이 다르다. `innerHTML`은 실제 DOM 노드를 전부 버리고 새로 만들고, 가상 DOM은 화면과 무관한 JS 객체를 새로 만든다. 실제 DOM은 비교 후 바뀐 곳만 고친다.

**Q. 가상 DOM 객체는 사람이 직접 고치나?**
A. 아니다. 사람은 state 값만 바꾼다. 새 가상 DOM을 만들고 비교하고 반영하는 일은 라이브러리가 자동으로 한다.

**Q. `setCount(2)`도 결국 DOM 수정 아닌가?**
A. 간접적이다. `setCount`는 JS 쪽 값을 바꾸고 다시 그리기를 예약할 뿐이다. 실제 DOM 수정은 그 뒤에 patch 단계에서, 필요할 때만 일어난다. 값이 같거나 화면에 쓰이지 않는 값이면 DOM은 바뀌지 않는다.

**Q. diff에서 DOM을 수정하나?**
A. 하지 않는다. diff는 JS 객체끼리 비교만 한다. 실제 DOM은 patch에서만 건드린다.

**Q. 노드를 "메모리에서 삭제한다"는 게 무슨 뜻인가?**
A. 먼저 부모와의 연결을 끊어 화면에서 빼고, 아무도 그 노드를 가리키지 않으면 브라우저가 나중에 메모리를 회수한다. 같은 글자의 노드를 새로 만들어도 **다른 객체**이므로, 이전 노드에 붙어 있던 이벤트·입력값은 사라진다.

**Q. 왜 비교를 실제 DOM이 아니라 가상 DOM에서 하나?**
A. 두 가지 이유다. 실제 DOM으로 두 벌을 만들면 비싸고, 실제 DOM은 화면에 보이는 한 벌뿐이라 새 화면을 만드는 순간 이전 화면이 덮여서 비교할 수 없다.
