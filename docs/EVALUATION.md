# 미니 리액트 팀원 프로젝트 평가기준

팀원들의 미니 리액트를 같은 기준으로 평가하고, 각자의 장점을 뽑아 하나로 합치기 위한 기준입니다.

## 기준끼리 겹치지 않게 나눈 범위

- 정상 입력에서 동작하는지는 **정확성**이 보고, 악의적인 입력을 막는지는 **보안**이 봅니다.
- 얼마나 빠른지는 **성능**이 보고, 자원을 제때 정리하는지는 **메모리**가 봅니다.
- 동작 자체는 **정확성**이 보고, 그 동작을 자동 테스트로 증명했는지는 **테스트**가 봅니다.
- **차별성**은 과제 범위 밖에 무엇을 더했는지만 봅니다. 더한 기능의 완성도는 나머지 기준으로 판정합니다.

## 기준 목록

| # | 기준 | 왜 필요한가 |
|---|------|-------------|
| 1 | 렌더링 성능 | VDOM을 쓰는 이유가 "바뀐 부분만 DOM에 반영"하는 데 있기 때문 |
| 2 | 사용성 | 검증 페이지와 데모를 처음 보는 사람도 바로 써 볼 수 있어야 하기 때문 |
| 3 | 메모리·자원 관리 | 오래 쓸수록 쌓이는 누수는 데모를 봐서는 드러나지 않기 때문 |
| 4 | 보안성 | 테스트 영역은 사용자가 쓴 HTML을 그대로 렌더링해서 XSS가 들어올 수 있기 때문 |
| 5 | 차별성 | 과제가 요구하는 항목이고, 합칠 때 한 사람 것에만 있는 기능을 찾는 데 쓰기 때문 |
| 6 | 요구사항 충족·정확성 | 다른 기준은 모두 "제대로 동작한다"는 전제가 있어야 의미가 있기 때문 |
| 7 | 테스트·검증 | 합칠 때 회귀를 막는 안전망이고, 과제 품질 기준이기도 하기 때문 |
| 8 | 코드 구조·합치기 쉬운 정도 | 장점을 뽑아 합치려면 모듈을 떼어 낼 수 있고 인터페이스가 맞아야 하기 때문 |
| 9 | 설명 가능성·문서 | 과제가 "핵심 로직을 직접 설명할 것"과 README 항목을 요구하기 때문 |

1~5는 처음 정한 기준이고, 6~9는 평가 전문가 관점에서 추가한 기준입니다.

## 기준별 확인할 것

### 1. 렌더링 성능
- patch가 바뀐 노드만 건드리는지 (DevTools나 MutationObserver로 변경 횟수 세기)
- 리스트 재조정 방식 (key를 쓰는지, 순서만 바뀔 때 DOM을 다시 만들지 않는지)
- 같은 조작을 했을 때 걸린 시간과 Reflow 횟수 (Performance 탭)

### 2. 사용성
- 실제 영역과 테스트 영역이 잘 구분되는지, 뒤로·앞으로 버튼이 이동할 곳이 없을 때 비활성화되는지
- 잘못된 HTML이나 빈 입력에 피드백을 주는지
- 데모가 입력이나 클릭에 즉시, 끊김 없이 반응하는지

### 3. 메모리·자원 관리
- useEffect의 cleanup이 다시 실행되기 전과 언마운트될 때 호출되는지
- 노드를 지우거나 교체할 때 이벤트 리스너도 함께 해제되는지
- history 배열에 크기 제한이 있는지, 이전 VDOM 참조가 남지 않는지 (Heap snapshot)

### 4. 보안성
- 텍스트를 넣을 때 textContent를 쓰는지, innerHTML을 쓰는지
- `on*` 속성이나 `javascript:` URL, `<script>` 태그를 막거나 무력화하는지
- 이벤트 핸들러를 문자열 속성이 아니라 함수로 연결하는지

### 5. 차별성
- 필수 범위 밖에서 추가한 기능 (batching, diff 시각화, 변경 로그, 개발 도구 등)
- 그 기능을 다른 구현에 떼어 붙일 수 있는지
- 데모 주제가 직접 만든 엔진의 장점을 잘 보여 주는지

### 6. 요구사항 충족·정확성
- diff 5가지 케이스(추가, 삭제, 타입 교체, 텍스트 변경, 속성 변경)와 자식 재귀 비교가 맞게 동작하는지
- Patch, history, 뒤로·앞으로 버튼을 눌렀을 때 두 영역이 함께 바뀌는지
- state가 바뀌면 VDOM 생성 → diff → patch 흐름을 재사용하는지, hook은 루트에서만 쓰고 자식은 순수 함수로 두는지

### 7. 테스트·검증
- 6개 모듈(VDOM 변환, diff, patch, useState, useEffect, useMemo)마다 단위 테스트가 있는지
- 화면 동작을 확인하는 기능 테스트(E2E)가 있는지
- 엣지 케이스(빈 자식, null, 중첩된 타입 교체, 연속 setState 등)를 테스트하는지, 명령 한 줄로 전부 통과하는지

### 8. 코드 구조·합치기 쉬운 정도
- vdom, diff, patch, hooks가 파일이나 모듈 단위로 나뉘어 있고 서로 의존이 적은지
- VDOM 노드 형태와 diff 결과(patch 목록) 형식이 문서화되어 있어 다른 구현과 맞출 수 있는지
- 이름, 타입(TS 사용 여부), 중복 코드처럼 읽기 쉬운지

### 9. 설명 가능성·문서
- README가 필수 설명 항목(Reflow/Repaint, MutationObserver, diff·patch 방식, 리렌더 예약, 실제 React와의 차이)을 다루는지
- 작성자가 hooks 배열과 인덱스로 상태가 유지되는 원리를 코드를 짚으며 설명할 수 있는지 (질의응답으로 확인)
- 설계 결정과 한계를 적어 두었는지

## 점수 매기는 법

| 점수 | 의미 |
|------|------|
| 0 | 없음 |
| 1 | 부분 충족 |
| 2 | 충족 |
| 3 | 모범 |

6~8번은 프로젝트 전체에 한 번 매기지 말고 **모듈별**(VDOM 변환, diff, patch, hooks, 검증 페이지, 데모)로 매깁니다. 그러면 "diff는 A 것, hooks는 B 것"처럼 모듈 단위로 고를 수 있습니다.

## 합칠 때 고르는 순서

1. 정확성(6)과 테스트(7)가 2점 이상인 모듈만 후보로 남깁니다.
2. 그중 코드 구조(8) 점수가 높은 구현을 뼈대로 삼습니다.
3. 다른 사람 구현에서 성능, 보안, 차별 기능 중 떼어 붙일 수 있는 것을 옮겨 붙입니다.
